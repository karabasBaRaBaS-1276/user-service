# Работа с базой данных

Данный документ описывает требования и особенности работы сервиса **user-service** с базой данных PostgreSQL. Информация предназначена для разработчиков и инженеров эксплуатации.

---

## Поддерживаемая СУБД

Сервис рассчитан на работу с **PostgreSQL**.

Рекомендуемая версия:

* PostgreSQL **15.x**

Более ранние версии могут работать, но официально не тестируются.

---

## Подключение к базе данных

Параметры подключения задаются в конфигурации приложения (`DatabaseConfig`) и включают:

* хост и порт PostgreSQL
* имя базы данных
* пользователя и пароль
* режим SSL
* имя схемы

Сервис **всегда подключается к явно указанной базе данных** и всегда подключается к явно указанной БД.

Техническая учетная запись (ТУЗ), по которой происходит подключение к БД, должна быть создана заранее. Как и сама БД. Обязательно раздать права ТУЗ на подключение к БД и на создание схем

```sql
GRANT CONNECT ON DATABASE <БД> TO <ТУЗ>;
GRANT CREATE ON DATABASE <БД> TO <ТУЗ>;
```

## Схема (schema)

Все таблицы сервиса размещаются в отдельной схеме PostgreSQL.

### Рекомендации

* Имя схемы должно совпадать с именем сервиса (например, `user_service`)
* Схема указывается в конфигурации приложения
* При инициализации соединения используется параметр `search_path`

Это позволяет:

* изолировать данные сервиса от других приложений
* упростить миграции
* избежать конфликтов имён таблиц

### Инициализация схемы

Создание и выбор схемы выполняется в коде приложения, в процессе инициализации подключения к БД:

После успешного подключения выполняется:

```sql
CREATE SCHEMA IF NOT EXISTS <schema_name>;
```

Затем схема устанавливается как схема по умолчанию:

```sql
SET search_path TO <schema_name>;
```

Таким образом:

* схема гарантированно существует к моменту запуска миграций
* все последующие SQL-операции выполняются в нужной схеме
* миграции не содержат жёстких ссылок на имя схемы

### Почему схема создаётся в коде, а не в миграциях

Данное решение принято осознанно:

* Go-миграторы (включая golang-migrate) не поддерживают подстановки переменных
* использование подстановок а-ля ${database.schema} в SQL-файлах невозможно без внешнего препроцессинга
* установка search_path на уровне соединения решает проблему универсально

Дополнительные последствия:

* создание схемы не откатывается
* схема рассматривается как часть инфраструктуры сервиса, а не как бизнес-миграция

## Миграции базы данных

### Общие правила

SQL‑миграции хранятся в каталоге:

```text
migrations/
```

Миграции:

* не содержат имени схемы
* используют обычные SQL-конструкции:

```sql
CREATE TABLE ...
```

* полагаются на корректно установленный search_path

### Структура файлов

Используется стандартная схема:

```text
000001_create_person.up.sql
000001_create_person.down.sql
000002_add_index_to_person.up.sql
000002_add_index_to_person.down.sql
```

* `.up.sql` — применение изменений
* `.down.sql` — откат изменений

### Формат имени файла

#### Общие требования

Используется следующий формат:

```text
NNNNNN_<action>_<entity_or_scope>.<direction>.sql
```

Где:

* `NNNNNN` — порядковый номер миграции (с ведущими нулями)
* `<action>` — тип изменения
* `<entity_or_scope>` — затрагиваемая сущность или логическая область
* `<direction>` — `up` или `down`

Пример:

```text
000005_seed_gloss_auth_client.up.sql
```

#### Правила нумерации

* Нумерация строго возрастающая
* Пропуски допустимы (например, если миграция была удалена)
* Переупорядочивание уже применённых миграций запрещено
* Новая миграция всегда получает номер больше существующих

#### Классификация миграций по типу (`<action>`)

##### 1. Структурные миграции (DDL)

Используются для изменения схемы БД.

Допустимые префиксы:

| Префикс  | Назначение                                |
| -------- | ----------------------------------------- |
| `create` | Создание таблиц, индексов, представлений  |
| `add`    | Добавление колонок, индексов, ограничений |
| `alter`  | Изменение существующих структур           |
| `drop`   | Удаление объектов                         |
| `rename` | Переименование объектов                   |

Примеры:

```text
000002_create_person.up.sql
000003_add_index_to_person.up.sql
```

##### 2. Миграции данных (DML)

Используются для изменения или наполнения данных.

Допустимые префиксы:

| Префикс    | Назначение                                     |
| ---------- | ---------------------------------------------- |
| `seed`     | Начальное обязательное наполнение системы      |
| `populate` | Массовое заполнение данных                     |
| `backfill` | Заполнение новых полей на основе старых данных |
| `fix`      | Коррекция некорректных данных                  |

Примеры:

```text
000005_seed_gloss_auth_client.up.sql
000010_backfill_user_active_flag.up.sql
```

⚠️ `seed`-миграции используются только для системных данных, без которых приложение не может функционировать.

##### 3.  Логика БД (функции, триггеры)

Используются для серверной логики PostgreSQL.

Рекомендуемые префиксы:

| Префикс             | Назначение               |
| ------------------- | ------------------------ |
| `add_function_to`   | Добавление функций       |
| `add_trigger_to`    | Добавление триггеров     |
| `alter_function_to` | Изменение логики функций |

Примеры:

```text
000007_add_function_to_person.up.sql
000008_add_trigger_to_person.up.sql
```

**Важно!** При работе с триггерами и функциями приходится явно указывать имя схемы в скрипте.

### Ответственность миграций

Миграции отвечают только за структуру данных, но не за:

* создание схемы
* выбор схемы
* параметры подключения

Эти задачи решаются на уровне инициализации БД в коде. По факту эта миграция № 000001, которая выполнена отдельно в коде без возможности отката.

## Кодировка и локализация сообщений

### Параметр `lc_messages`

PostgreSQL использует параметр `lc_messages` для определения языка и кодировки сообщений об ошибках.

Для корректного отображения ошибок (в логах и консоли) рекомендуется значение:

```sql
SHOW lc_messages;
```

```text
Russian_Russia.utf8
```

При другом значении сообщения об ошибках могут:

* отображаться в неожиданной кодировке
* быть неудобными для чтения
* некорректно логироваться

### Где настраивается

Файл конфигурации PostgreSQL можно определить командой:

```sql
SHOW config_file;
```

После изменения параметров требуется перезапуск сервера PostgreSQL.

## SSL и безопасность соединения

Режим SSL задаётся параметром `ssl_mode`.

Поддерживаемые значения соответствуют официальной документации PostgreSQL:

* `disable`
* `allow`
* `prefer`
* `require`
* `verify-ca`
* `verify-full`

Для production-окружений рекомендуется использовать `require` или более строгие режимы.

## Интеграционные тесты

Для проверки работы с базой данных используются **интеграционные тесты** с реальной PostgreSQL.

### Подход

* PostgreSQL поднимается в Docker‑контейнере
* используется библиотека `testcontainers-go`
* контейнер создаётся один раз на пакет через `TestMain`
* данные очищаются между тестами

### Требования

* установлен Docker
* разрешён запуск контейнеров

### Запуск

```bash
go test -tags=integration -v -count=1 ./internal/app
```

## Общие рекомендации

* используйте отдельную схему на сервис
* управление схемой выполняйте централизованно в коде
* SQL-миграции должны быть независимы от окружения
* храните все миграции под версионным контролем
